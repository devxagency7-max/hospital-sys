# نموذج الفوترة — Invoice / Payment / Refund / Credit Note

قرار معماري يُغلق قبل أي شاشة فوترة في المرحلة 1. يُجيب عن سؤال واحد كان
غائبًا في المرحلة 0: **حين تحتاج قيمة فاتورة إلى تصحيح، هل نُنشئ "مرتجعًا"
أم شيئًا آخر؟**

التنفيذ الكامل في [`frontend/js/domain/billing.js`](../frontend/js/domain/billing.js)،
مُغطّى بـ 175 اختبارًا في
[`frontend/tests/billing.test.mjs`](../frontend/tests/billing.test.mjs) و
[`frontend/tests/data.test.mjs`](../frontend/tests/data.test.mjs). هذا الملف
هو القرار؛ ذاك هو التنفيذ.

---

## 1. لماذا كان هذا قرارًا لا تفصيلاً

في المرحلة 0 كان مفهوم "مرتجع" واحد يُستخدم لحالتين مختلفتين تمامًا:

- مريض دفع بالخطأ مرتين → نُعيد له مالًا. **هذا مرتجع فعلي.**
- فاتورة فيها بند لم تُقدَّم خدمته → القيمة المستحقة نفسها خاطئة. **هذا ليس
  مرتجعًا؛ لا أحد طلب استرداد مال بعد.**

خلط الحالتين تحت اسم واحد أنتج تناقضًا فعليًا بين الشاشات مرتين متتاليتين
أثناء بناء هذا المشروع (موثَّق في تاريخ الـ commits). القرار هنا يمنع تكرار
ذلك بنيويًا: **الحالتان كيانان منفصلان، لكل منهما حقوله وحالته ومساره.**

## 2. المصطلحات

### Invoice — الفاتورة

مستند مالي يمر بثلاث مراحل حياة لا رجوع فيها إلى الخلف:

```text
draft ──issueInvoice()──▶ issued ──cancelInvoice()──▶ cancelled
  │                          │
  │ قابلة للتعديل الكامل      │ مستند نهائي — total/discount/tax مجمَّدة
  │ لا التزام مالي بعد        │ أي تصحيح لاحق عبر Credit Note لا تعديل مباشر
```

- **draft**: بنود وخصم وضريبة قابلة للتعديل بحرية. لا تدخل أي كشف حساب ولا
  أي مجموع مديونية — المريض لا يُحاسَب على مسودة.
- **issued**: لحظة `issueInvoice()`، تتجمَّد `total` و `discount` و `tax`
  إلى الأبد. هذا هو المستند الذي قد يُطبَع أو يُرسَل لمنظومة الفاتورة
  الإلكترونية. **لا توجد دالة "تعديل فاتورة صادرة"** — ومحاولة أي كتابة على
  بنودها ترمي خطأ `BUSINESS_RULE_VIOLATION` عبر `assertMutable()`.
- **cancelled**: نهائية ولا رجوع عنها. تحتفظ بـ `total` وبنودها للتدقيق، لكن
  كل حقل مالي آخر (`paid`, `refunded`, `credited`, `remaining`) يُصفَّر.
  فاتورة أُلغيت بالخطأ تُصحَّح بفاتورة جديدة، لا بإعادة تفعيل القديمة — وإلا
  فقد سجل الإلغاء نفسه قيمته كدليل تدقيق.

### Payment — الدفعة

مال استلمه المستشفى فعليًا مقابل فاتورة صادرة. دفعات متعددة على فاتورة واحدة
مسموحة (تقسيط). **الدفعة لا تُعدَّل ولا تُحذف بعد تسجيلها** — تصحيح خطأ في
دفعة مسجَّلة يتم بتسجيل حركة مقابلة (مرتجع)، لا بتعديل السجل الأصلي.

### Refund — المرتجع

**مال عاد فعليًا للمريض. يؤثر على جانب التحصيل (Payment side) فقط.**

```text
صافي المحصَّل (netPaid) = Σ(الدفعات) − Σ(المرتجعات المعتمدة)
```

قيمة الفاتورة نفسها (`total`) لا تتغيّر. فاتورة مُسدَّدة بالكامل اعتُمد عليها
مرتجع جزئي **تعود `partially_paid`** — وهذا صحيح: الخدمة كانت صحيحة والمستحق
لم يتغيّر، لكن ما حُصِّل فعليًا نقص.

**مثال:** فاتورة 1000، دُفعت بالكامل، ثم اعتُمد مرتجع 400 (تحصيل مزدوج
اكتُشف لاحقًا) → `netPaid = 600`، `remaining = 400`، الحالة `partially_paid`.

### Credit Note — إشعار الدائن

**تصحيح لقيمة الفاتورة نفسها بعد إصدارها. يؤثر على جانب الفاتورة (Invoice
side) فقط — لا حركة نقدية مصاحبة له بالضرورة.**

```text
effectiveTotal = total − Σ(إشعارات الدائن المعتمدة)
```

لا حقل "طريقة دفع" في إشعار الدائن — لأن لا مال يتحرك. الفرق الجوهري عن
المرتجع ملموس في شكل البيانات نفسه، لا في التسمية فقط.

**مثال:** فاتورة 1000 لم يُدفع عليها شيء بعد، اكتُشف أن بندًا بقيمة 300 لم
يُقدَّم → `effectiveTotal = 700` فورًا، رغم أن `paid` لا يزال صفرًا.

### Outstanding Balance — الرصيد المستحق

**الصيغة الكاملة التي تجمع المحورين:**

```text
effectiveTotal = total − Σ(إشعارات دائن معتمدة)
netPaid        = Σ(دفعات) − Σ(مرتجعات معتمدة)
remaining      = effectiveTotal − netPaid
```

هذا هو "الرصيد المستحق" — موجب يعني على المريض، صفر يعني مسدَّدة بالكامل.
هذه الصيغة الموحَّدة في `settleInvoice()` هي **الدالة الوحيدة** التي تحسب
`remaining` في كامل النظام؛ لا شاشة ولا endpoint يحسبها بنفسه.

### Overpayment — الدفع الزائد

حين يكون `netPaid > effectiveTotal`، فإن `remaining` سالب. هذا ليس خطأ —
الحالة `overpaid` مسجَّلة رسميًا. يحدث بسببين مختلفين جوهريًا:

1. **تحصيل مباشر زائد**: دُفع 1200 على فاتورة قيمتها 1000 (خطأ كاشير مثلاً).
2. **إشعار دائن بعد تحصيل كامل** — الحالة الحرجة التي كانت سبب الالتباس
   الأصلي: فاتورة 1000 دُفعت بالكامل، ثم صدر إشعار دائن 300 (خدمة لم
   تُقدَّم) → `effectiveTotal = 700`، لكن `netPaid` لا يزال 1000 →
   `remaining = -300`. **المريض له رصيد دائن 300، لا عليه مديونية.**

`summarizePatientAccount()` يُترجم أي رصيد سالب إلى `summary.creditBalance`
موجب للعرض. تحويل هذا الرصيد الدائن إلى مال فعلي يعود للمريض هو **مرتجع
لاحق منفصل** — خطوة عمل إنسانية (قرار موظف الفوترة)، وليست نتيجة تلقائية
لإشعار الدائن.

### Cancellation — الإلغاء

يُلغي الفاتورة بأكملها. يتطلب سببًا إلزاميًا (`cancelInvoice({ reason })`) —
بلا سبب، لا يوجد دليل تدقيق على سبب محو التزام مالي كان قائمًا. فاتورة
ملغاة لا تدخل أي كشف حساب ولا أي مجموع نظام، وتحتفظ بإجمالي أصلي ثابت
للمراجعة فقط.

## 3. العلاقة بين الكيانات

```text
                         ┌─────────────┐
                         │   Invoice   │ total (مجمَّد بعد issue)
                         └──────┬──────┘
                 ┌──────────────┼──────────────┐
                 │              │              │
          ┌──────▼─────┐ ┌──────▼──────┐ ┌─────▼──────┐
          │  Payment   │ │   Refund    │ │ CreditNote │
          │ (1..n)     │ │ (0..n)      │ │ (0..n)     │
          │            │ │ pending/    │ │ pending/   │
          │ لا تعديل    │ │ approved/   │ │ approved/  │
          │ بعد الحفظ   │ │ rejected    │ │ rejected   │
          └──────┬─────┘ └──────┬──────┘ └─────┬──────┘
                 │              │              │
            Σ = paid     Σ(معتمد) = refunded   Σ(معتمد) = credited
                 │              │              │
                 └──────┬───────┘              │
                         │                      │
                 netPaid = paid − refunded      │
                         │                      │
                         │    effectiveTotal = total − credited
                         │                      │
                         └──────────┬───────────┘
                                    │
                      remaining = effectiveTotal − netPaid
                                    │
                                    ▼
                    status: unpaid / partially_paid /
                            paid / overpaid
```

**الاستقلال التام بين Refund و CreditNote هو جوهر هذا النموذج.** كل محور
يعدّل طرفه فقط، فيتركّبان بلا أي حالة خاصة: فاتورة قد تحمل مرتجعًا بلا إشعار
دائن، أو إشعارًا دائنًا بلا مرتجع، أو كليهما معًا — والصيغة واحدة في كل
الحالات. هذا مُختبَر صراحة على بيانات حقيقية (لا افتراضية فقط) في
`tests/data.test.mjs`.

### مثال مركّب كامل

فاتورة 1000، دُفعت بالكامل (1000)، ثم:
- اعتُمد إشعار دائن 200 (بند لم يُقدَّم) → `effectiveTotal = 800`
- اعتُمد مرتجع 150 (ردّ جزء من الفائض نقدًا) → `netPaid = 850`

```text
remaining = 800 − 850 = −50   →   overpaid، رصيد دائن 50
```

نفس المعادلة بالأرقام أعلاه مُختبرة حرفيًا في `tests/billing.test.mjs` (قسم
"التسوية — مرتجع وإشعار دائن معًا"). ونفس *السيناريو* — مرتجع وإشعار دائن
معتمدان معًا على فاتورة واحدة، بأرقام مختلفة — موجود فعليًا في البيانات
التجريبية الحالية: `INV-2026-0001` (راجع `#/design-system?tab=data` أو
`GET /invoices/2001`).

## 4. ما لا يُسمح به أبدًا

| القاعدة | أين تُطبَّق |
|---|---|
| لا تعديل صامت لفاتورة صادرة | `assertMutable()` ترمي `BUSINESS_RULE_VIOLATION` |
| لا حذف لمرتجع أو إشعار دائن بعد المراجعة | `assertDocumentMutable()` — الانتقال من `pending` لمرة واحدة فقط |
| لا مرتجع أو إشعار دائن على فاتورة غير صادرة | `maxRefundable()` / `maxCreditable()` تُعيدان صفرًا على مسودة أو ملغاة |
| لا تجاوز الإجمالي الأصلي بإشعارات الدائن | `effectiveTotal` محروس بـ `money.max(…, 0)` |
| لا تجاوز المحصَّل فعليًا بالمرتجعات | `maxRefundable()` = `paid − refunded السابق`، لا تقل عن صفر |
| لا إلغاء بلا سبب مُسجَّل | `cancelInvoice()` ترمي خطأ بلا `reason` |
| لا حساب مالي خارج `js/domain/billing.js` | اختبار معماري في `tests/architecture.test.mjs` |

## 5. السجل الزمني (Audit Trail)

لا يوجد جدول "أحداث" منفصل يحتاج هو نفسه حراسة من التعديل. الضمانة الحقيقية
أبسط: **كل دفعة ومرتجع وإشعار دائن ثابت بعد إنشائه** — `status` ينتقل مرة
واحدة فقط (`pending → approved` أو `pending → rejected`)، ولا شيء آخر فيه
يتغيّر. بما أن المصادر ثابتة، فإعادة بنائها إلى سجل زمني مُرتَّب تُعيد نفس
النتيجة دائمًا — وهذا ما تفعله `buildInvoiceTimeline()`: عرض مُشتَق لا سجل
مُخزَّن، يضم حدث الإصدار وكل دفعة ومرتجع وإشعار دائن وحدث الإلغاء إن وُجد،
مرتَّبة زمنيًا.

كل فاتورة في الـ API التجريبي تُعيد هذا السجل عبر `GET /invoices/:id` في
حقل `timeline`.

## 7. ما تعمَّدنا عدم تحديده

هذه قرارات عمل تخص المستشفى نفسه، لا قرارات نموذج بيانات — تُترك صراحة
لمرحلة لاحقة ولصاحب القرار التجاري:

- **من له صلاحية اعتماد مرتجع أو إشعار دائن؟** النموذج يوفّر `status` ثلاثي
  فقط. سير الموافقة (مرحلة واحدة أم أكثر، حدود مبلغ تستدعي موافقة أعلى) قرار
  تنظيمي بحت.
- **هل الدفع الزائد يتحوّل تلقائيًا إلى مرتجع، أم يبقى رصيدًا دائنًا
  يُستخدم في فاتورة قادمة؟** النموذج يعرض `creditBalance` فقط ولا يفرض
  تحويله.
- **حدود زمنية** (لا يُقبل مرتجع بعد X يومًا من الفاتورة) — غير مفروضة.
- **علاقة إشعار الدائن ببنود الفاتورة** (هل يستهدف بندًا محددًا أم الفاتورة
  ككل؟) — النموذج الحالي يتعامل مع إشعار الدائن كمبلغ إجمالي على مستوى
  الفاتورة، لا كتصحيح لبند بعينه.

لا تُبنَ شاشة Phase 1 تفترض إجابة لأي من هذه الأسئلة دون طرحها على صاحب
المنتج أولاً.
